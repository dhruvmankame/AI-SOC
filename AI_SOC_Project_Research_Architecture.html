1. Executive recommendation

Recommended project direction: build an evidence-first AI-SOC with two separate planes: a high-throughput Detection Plane that processes every event cheaply, and a selective Agentic Investigation Plane that only activates for correlated, high-value alerts. This is more realistic, measurable and efficient than sending raw logs to an LLM.
1

Detection Plane

Parsing, OCSF normalization, Sigma/IOC checks, statistical signals, deep sequence anomaly detection and entity risk scoring.

2

Correlation Plane

Deduplicate signals, group events by entity/time/causal relationships, build a case and calculate an incident risk score.

3

Agentic Investigation Plane

Specialist agents query evidence, CTI, ATT&CK mappings and historical cases, then produce a cited investigation narrative and recommended next steps.

Recommended frontend: Next.js + TypeScript + Tailwind CSS + ECharts/Apache ECharts + React Flow. Recommended backend: FastAPI + Python. Recommended orchestration: LangGraph. Primary telemetry store: ClickHouse. Operational store: PostgreSQL with pgvector. Streaming: Redpanda (Kafka API compatible) or Kafka. ML: PyTorch + scikit-learn + MLflow. Collector: Vector or Fluent Bit.

The project's defensible novelty should be: (a) tiered inference that minimizes expensive AI usage, (b) evidence-linked multi-agent investigations, (c) combined rule + statistical + deep sequence + behavior detection, (d) transparent risk fusion, (e) reproducible evaluation on public datasets, and (f) explicit AI safety controls.

2. Detailed problem statement

Modern Security Operations Centers must ingest telemetry from endpoints, operating systems, cloud services, applications, identity platforms, network devices and security tools. The difficult part is not simply storing logs; it is converting heterogeneous, noisy events into a small number of trustworthy incidents that an analyst can understand and act on quickly.

Core problems the system must solve

ProblemWhy it is difficultProject response
Heterogeneous log formatsDifferent vendors use different fields, timestamps, names and semantics.Collector transforms + parser templates + OCSF-aligned common event model.
High event volumeMost events are benign; applying expensive models to every event wastes compute.Streaming filters, deduplication, rules and lightweight scoring before deep/LLM inference.
Known + unknown attacksRules detect known behavior but miss novel patterns; anomaly models can be noisy.Hybrid detection: Sigma/IOC + statistical + supervised ML + sequence anomaly + UEBA.
Alert fatigueIndividual alerts often represent fragments of one attack.Entity/time correlation and incident clustering before analyst presentation.
Slow investigationAnalysts pivot manually across users, hosts, processes, IPs and threat intelligence.Specialist investigation agents working over structured evidence and common incident state.
LLM hallucinationAn AI can produce plausible but unsupported explanations.Evidence IDs, source provenance, constrained tools, verifier agent and “unsupported claim” rejection.
Unsafe automationAutonomous containment can disrupt production.Recommendation-first workflow; approvals for high-impact actions; simulation mode by default.
Changing environmentsNormal behavior and log templates drift over time.Model monitoring, template drift tracking, retraining pipeline and analyst feedback loop.
Formal research question: Can a hybrid, multi-stage AI-SOC reduce the number of events requiring expensive analysis while maintaining or improving threat-detection quality, and can a multi-agent investigation layer produce faster, evidence-grounded incident narratives than a single-agent or manual-style baseline?

Suggested academic problem statement

“Existing SOC workflows face challenges in heterogeneous telemetry normalization, alert volume, false positives and manual investigation overhead. This project proposes a multi-agent deep learning system that combines real-time log normalization, hybrid threat detection, sequence-based anomaly detection, entity behavior analytics, alert correlation and evidence-grounded agentic investigation. The system is evaluated on detection quality, alert reduction, investigation latency, evidence coverage, hallucination rate and computational cost.”

3. Goals, scope and non-goals

Must implement

  • Multi-source log ingestion: JSON, Syslog and CSV replay.
  • Parsing, normalization and enrichment into a common schema.
  • Real-time searchable log store.
  • Sigma-like rule engine and IOC matching.
  • Deep-learning anomaly model over log-event sequences.
  • Behavior/entity risk scoring.
  • Alert deduplication and incident correlation.
  • Multi-agent incident investigation with evidence provenance.
  • MITRE ATT&CK mapping and timeline/attack graph.
  • Analyst dashboard, live alerts, incident workbench and model metrics.
  • Human approval boundary for response actions.
  • Training/evaluation pipeline with documented benchmarks.

Keep outside the MVP

  • Trying to replace a production enterprise SIEM at petabyte scale.
  • Fully autonomous endpoint isolation or account deletion.
  • Malware reverse engineering and exploit generation.
  • Dozens of proprietary commercial integrations.
  • Training a foundation LLM from scratch.
  • Building a full endpoint agent or EDR kernel driver.
  • Claiming “zero false positives.”

These can be presented as future work rather than weakening the core prototype with too much scope.

Primary thesis

“Selective intelligence beats universal intelligence.” The data plane should be deterministic and highly optimized. Deep learning should evaluate sequences/windows where context is required. LLM agents should investigate incidents—not parse every log line.

6. Research foundations

Log parsing and representation

Drain is a classic online log parser using a fixed-depth parse tree; its original evaluation emphasized streaming/timely parsing and reported faster runtime than contemporary parsers on tested datasets. [S16] A 2024 empirical study found that parsing choices can materially affect downstream anomaly-detection accuracy, so parsing must be treated as part of the ML system, not just preprocessing. [S17]

Deep sequence anomaly detection

DeepLog models log keys as a sequence using LSTM and flags deviations from learned normal patterns. [S18] LogAnomaly combines semantic template representation with sequential and quantitative anomaly detection. [S19] LogBERT applies self-supervised BERT-style learning to normal log sequences. [S20] LogGPT uses GPT-style next-event prediction and reinforcement-learning fine-tuning for anomaly detection. [S21]

Important evidence for model selection: a 2025 comprehensive comparison across seven log datasets reported that supervised traditional ML and deep-learning techniques can be close in accuracy/prediction time, with traditional supervised methods less sensitive to hyperparameter tuning. This supports keeping strong baselines in the project rather than assuming “deep = always better.” [S22]

Multi-agent SOC research

Recent research is moving toward evidence-grounded specialist agents. The 2025 IEEE Cognitive SOC work used Triage, Enrichment and StoryWeaver agents and explicitly measured evidence linkage/citation coverage and hallucination. [S23] A 2025 agentic-SOAR study proposed investigation, validation and active-monitoring stages, emphasizing validation instead of unconstrained autonomy. [S24]

Standards to adopt

  • OCSF: vendor-agnostic, open cybersecurity event schema suited to normalization. [S25]
  • Sigma: portable YAML detection rules for suspicious behavior in logs. [S26]
  • MITRE ATT&CK: common knowledge base/taxonomy for adversary tactics and techniques. [S27]
  • NIST SP 800-61 Rev. 3: current incident-response recommendations aligned with CSF 2.0. [S28]

9. Threat detection and deep-learning design

9.1 Detection ensemble

DetectorBest forImplementation
Rule detectorKnown TTPs, policy violations, deterministic patternsSigma subset compiled to internal predicates / ClickHouse SQL.
IOC detectorKnown malicious IP/domain/hashHash tables / dictionaries with TTL and source freshness.
Statistical detectorRate spikes, unusual frequencies, new destinationsZ-score / EWMA / robust quantiles / rolling baselines.
Supervised baselineLabeled datasets such as UNSW-NB15/CICIDSLogistic Regression / Random Forest / LightGBM for benchmark comparison.
Deep sequence modelAbnormal event ordering and contextSmall Transformer encoder or LSTM over template IDs + semantic embeddings.
AutoencoderMultivariate anomaly in feature windowsDenoising autoencoder, reconstruction-error threshold.
UEBAUser/host behavior deviationPer-entity baseline + temporal features; optional sequence model.

9.2 Recommended deep model for the final project

Contextual Log Transformer

Input window: last N normalized events for one entity/session, each represented by template ID embedding + semantic template embedding + categorical embeddings (source, event class, severity) + numeric time-gap/frequency features.

Architecture: embedding projection → 2–4 Transformer encoder blocks → pooled representation → heads for next-event prediction, anomaly score and optional attack-class classification.

Training: self-supervised on normal sequences first; optionally fine-tune with labeled anomalies. Keep DeepLog/LSTM and a traditional model as baselines.

Why this is suitable: it clearly satisfies the “deep learning” component, captures sequence context, remains small enough for a student deployment, and can be compared against established DeepLog/LogBERT ideas without needing a large foundation model.

9.3 Risk fusion

Use a transparent score rather than letting an LLM decide severity. Example:

risk = sigmoid(
    1.6 * rule_confidence
  + 1.3 * deep_anomaly_score
  + 1.1 * ueba_score
  + 1.4 * ioc_score
  + 0.8 * asset_criticality
  + 0.7 * correlation_strength
  - 0.9 * known_benign_score
)

Weights should be calibrated on validation data. Show the contribution of each component in the UI (“why this incident is high risk”).

9.4 Correlation rules

  • Same user + multiple failed logins + success + privilege event within a sliding window.
  • Suspicious process creation followed by outbound connection from same host.
  • Rare destination domain across organization + new executable + credential event.
  • Multiple low-severity alerts sharing user/host/IP within 10–30 minutes.
  • Sequence matches partial ATT&CK chain (e.g., initial access → execution → discovery → lateral movement).

Use OCSF concepts as the external/common schema because OCSF explicitly targets vendor-agnostic cybersecurity event normalization. [S25] You do not need to implement the entire OCSF specification; support a focused subset relevant to your sources.

10.2 Core tables

  • events (ClickHouse): immutable normalized telemetry.
  • signals (ClickHouse/Postgres): detector outputs with model/rule version.
  • alerts (Postgres): deduplicated analyst-facing alerts.
  • incidents (Postgres): correlated cases and state.
  • incident_entities: users/hosts/IPs/processes connected to incident.
  • evidence: evidence ID, source event IDs, provenance, confidence.
  • agent_runs: agent, prompt/template version, tools, citations, latency, token/compute cost, result status.
  • detection_rules: versioned rules, ATT&CK mapping, enabled state.
  • models: MLflow model/version metadata and thresholds.
  • feedback: analyst true-positive/false-positive/correction labels.

10.3 Evidence-first rule

Every narrative sentence that makes a factual claim about the incident should be traceable to one or more evidence_id values. The report agent receives verified facts, not raw free-form agent thoughts.

14. Security, privacy and AI guardrails

Because the project gives AI agents access to security telemetry and tools, the agents themselves become part of the attack surface. OWASP's current GenAI guidance includes prompt injection, sensitive-data disclosure, excessive agency and related risks; the Agentic Top 10 also focuses specifically on autonomous systems. [S38] [S39]

RiskControl
Prompt injection inside logsTreat log text as untrusted data; agents never follow instructions found in telemetry. Structured tools return fields/evidence, not raw instructions.
Excessive agencyRead-only tools by default; action tools separated by policy; high-impact actions require approval.
Sensitive log leakageRedact secrets/tokens; field allowlists; local model option; never send raw credentials to external LLM.
HallucinationEvidence-citation requirement; verifier agent; “unknown” is acceptable; no uncited factual conclusions.
Unsafe generated queriesGenerate query AST/DSL, validate it, enforce row/time limits, read-only DB account.
Data poisoningSeparate training datasets from live logs; model registry lineage; analyst-approved labels; anomaly on label distribution.
Supply-chain riskPin dependencies, scan containers, SBOM, signed model artifacts/checksums.
Audit failureImmutable agent/tool audit records: who/what/when/input hash/output/evidence/approval.

  • Analyst: investigate, comment, label alerts.

15. How to make the project more efficient than a naive AI-SOC

15.1 Compute funnel

100% events
  ↓ edge filter / dedupe / parse
20–60% normalized events requiring full persistence or feature updates
  ↓ rules + IOC + statistical gates
1–10% suspicious windows
  ↓ deep model / UEBA
0.1–2% alerts
  ↓ correlation
0.01–0.5% incidents
  ↓ multi-agent LLM investigation
human reviews only highest-value cases

The percentages are design targets to measure and tune, not assumed production facts.

15.2 Efficiency mechanisms

  • Edge reduction: drop known noise fields, deduplicate exact repeats, normalize before central ingestion.
  • Template compression: store template IDs and extracted variables for modeling while retaining raw pointer/hash for forensics.
  • Batch inference: score sequence windows in batches, not one GPU/CPU call per event.
  • Adaptive model routing: simple model for obvious cases; advanced model only for uncertainty band.
  • Materialized views: ClickHouse aggregates for repeated dashboard/risk features.
  • Incident-level RAG: retrieve only related evidence; never send entire log corpus to the LLM.
  • Cache enrichments: IOC/GeoIP/CVE results with TTL to avoid repeated external calls.
  • Token budgets: max investigation steps/tokens/tool calls; stop when confidence/evidence threshold is met.
  • Parallel specialists: evidence and threat-intel tasks can run concurrently, but merge through one verifier.
  • Model observability: detect drift and threshold degradation before expensive retraining.

15.3 Why ClickHouse

ClickHouse explicitly targets high-volume real-time analytics, observability and cybersecurity workloads; its current cybersecurity materials emphasize continuous high-throughput ingest and concurrent analytics. [S34] This is a better fit for immutable event analytics than using PostgreSQL as the only log database.

  • Events per second ingested and normalized.
  • p50/p95 event-to-alert latency.
  • ClickHouse query p95 for common investigation queries.
  • CPU/RAM/GPU utilization per 1,000 events.
  • Queue lag and dropped-event count (should be zero under designed load).
  • Agent orchestration p50/p95 duration.

16.4 Experiments to run

  1. Baseline ML: Random Forest/LightGBM vs LSTM/Transformer on the same labeled dataset.
  2. Parser ablation: structured ground-truth fields vs Drain templates vs naive tokenization.
  3. Hybrid ablation: rules only; ML only; rules + ML; rules + ML + correlation.
  4. Agent ablation: single-agent RAG vs multi-agent + verifier.
  5. Efficiency ablation: LLM every alert vs risk-gated LLM investigation.
  6. Evidence test: percentage of claims with valid evidence references.

17. Recommended datasets

DatasetUse in projectNotes
Loghub HDFS / BGL / OpenStack Log parsing + sequence anomaly benchmarking. Loghub provides many real-world system log datasets; HDFS, BGL and others include labels suitable for anomaly research. [S40]
UNSW-NB15 Supervised network intrusion baseline and attack classification. About 2.54M records, nine attack categories and published train/test subsets. [S41]
CSE-CIC-IDS2018 Network + host/security-log scenarios, more varied intrusion classes. Includes PCAPs and Windows/Ubuntu event logs along with extracted flow features. [S42]
LANL multi-source cyber events Entity correlation, authentication behavior and red-team ground truth. 58 days of de-identified auth/process/DNS/network-flow events with red-team events. [S43]
TON_IoT Heterogeneous IoT/OS/network data; optional generalization study. Includes telemetry, Windows/Linux OS datasets and network traffic. [S44]

Recommended dataset strategy

Use two datasets for the final evaluation, not five. A strong combination is Loghub HDFS/BGL for sequence anomaly detection plus LANL or CSE-CIC-IDS2018 for security-centric correlation/investigation. Keep UNSW-NB15 as a simple labeled baseline if compute/time is limited.

Definition of done by milestone

M1 — Pipeline complete

A log file or Syslog generator can stream data; normalized events are searchable in ClickHouse; dashboard shows events/sec and source health.

M2 — Detection complete

Rules + at least one ML detector create explainable alerts with detector reason, score and source events.

M3 — Deep learning complete

Trained model version is registered in MLflow and evaluated against at least one baseline using fixed splits.

M4 — Incident correlation complete

Multiple related alerts merge into a single incident with entities, timeline, risk contributors and ATT&CK tags.

M5 — Agentic investigation complete

An incident triggers agents that produce a cited evidence packet, hypotheses, verifier result and final report; tool calls are audited.

M6 — Final system complete

Frontend, APIs, evaluation notebook/scripts, Docker deployment, security controls, demo fixtures and documentation all run reproducibly.

21. Risks, limitations and how to discuss them

RiskMitigation / honest limitation
Public datasets are old or syntheticUse multiple sources and state that generalization to a live enterprise requires validation.
Class imbalanceUse PR-AUC/F1, stratified splits and class weighting; avoid accuracy-only reporting.
Data leakage in sequence windowsSplit chronologically or by session/host where appropriate; fit scalers/templates carefully.
Deep model may not beat simple baselineThat is a valid result; analyze where sequence context helps rather than forcing a claim.
LLM output variabilityUse structured schemas, low temperature, evidence verifier, fixed evaluation fixtures and multiple runs.
Threat intel network dependenceCache and ship offline fixtures for reproducible demos.
Too many infrastructure componentsDocker Compose profiles: core, ml, full; make Qdrant/Kubernetes optional.
Response automation riskSimulation by default; high-impact actions remain human-approved.
