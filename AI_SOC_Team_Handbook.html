AI-SOC Team handbook · knowledge transfer

An AI security operations centre where no claim survives without evidence.

AI-SOC ingests network-flow logs, detects attacks with deterministic code, correlates them into incidents, and then runs a four-agent LLM investigation whose every factual claim is pinned to a stored evidence record. A fail-closed verifier deletes any claim it cannot support. This handbook is the complete picture: architecture, the four agents, the data model, how to run it, what the numbers actually say, and where it is honestly weak.

01

What AI-SOC is

A working research prototype of a security operations centre. It is not a Splunk or Sentinel replacement and does not try to be. It is one coherent end-to-end loop, built to prove a single claim about how LLMs should be used in security work.

The loop, in the order a user experiences it:

1 · Upload a flow CSV 2 · Detect 3 · Correlate into incidents 4 · Investigate with agents 5 · Verify every claim 6 · Read the incident record 7 · Measure the result

A user opens the Analyze page, drops in a CICIDS or CICFlowMeter-format .csv, and a local backend runs detection on that file alone. Every flow that trips a detector becomes a signal; signals are grouped into incidents; the incidents are written to Postgres; and then the agent graph runs over each one automatically, streaming its progress back to the page. The result lands in the Incident Record: entities, cited evidence, the agent's report, and the verifier's verdicts — including the claims it threw away.

The prototype is deliberately honest about its own reach. It detects three attack families with real, independent detectors. For roughly eighteen further attack classes it carries the dataset's own label through the pipeline and investigates it, but marks that as an annotation rather than a detection. Section 07 explains exactly which is which.
02

The thesis, and the problem it answers

Selective intelligence beats universal intelligence.

Most "AI SOC" demos hand logs to a language model and print whatever it says. That fails in security work for a specific reason: an analyst cannot act on a finding they cannot audit. A confident sentence about an intrusion is worthless if nothing underneath it can be checked.

AI-SOC's answer has three parts:

  1. Deterministic code does the work that must be reproducible. Detection, correlation, risk scoring, and standardisation are Python and SQL. No model touches them. The same file always produces the same incidents.
  2. LLMs are used only after an incident already exists, and only to reason over evidence that has already been retrieved. They never decide what to look at next, and they never call a tool on their own.
  3. Every factual claim carries a citation, and a verifier that can only say no. If a claim's citations do not resolve, or the cited text does not actually entail the claim, the claim is deleted — not softened, not caveated. A rejected incident produces no report at all.
This is the part that must not be cut. Any change that makes the system more impressive by letting unsupported claims through is a regression against the project's actual contribution. Section 12 shows the measured effect: unverified, 25% of asserted claims were unsupported; with the verifier, 0%.
03

Two planes

The architecture splits at a hard line. Everything left of the line is deterministic and cheap; everything right of it costs an LLM call and only runs for incidents that earned one.

Detection plane

Python 3, standard library only. Streams the CSV twice — once to build per-cluster aggregates, once to detect and store. Never reads the dataset's Label column for detection. Writes nothing to the database itself; it emits JSON on stdout and the Node backend does the inserts.

ml/soccore.py ml/analyze.py ml/ingest_cicids.py

Investigation plane

TypeScript on LangGraph.js. One incident in, one incident-scoped evidence set out, four bounded LLM calls, every tool call and verdict audited into agent_runs. Control flow is fixed code — the graph is a straight line, with no conditional edges.

agents/src/graph.ts agents/src/agents/*.ts agents/src/server.ts
Why the controller is not an LLM. Letting a model choose which tool to call next makes the run unauditable, opens a prompt-injection surface, and blows the per-incident token budget on traversal instead of reasoning. Here each node calls one specialist with a fixed job and a structured-output schema. The graph is collect → hypothesize → verify → write_report, full stop.
04

The four-stage pipeline

This is the operational view of the same system. Stage 1 is code. Stages 2 to 4 are the agents, numbered 1 to 4 in the backend logs as AGENT 1/4 through AGENT 4/4.

STAGE 1

Standardize

A raw uploaded file becomes canonical records. Header aliases are resolved, timestamps parsed, unusable rows dropped, and each surviving flow assigned to exactly one incident. Deterministic Python — no model, no tokens, no variance.

emits → events, signals, incidents
engine → ml/analyze.py
STAGE 2

Identify

Agent 1 collects the incident's real events and distils them into checkable evidence facts, then a code gate deletes any fact citing an event that does not exist. Agent 2 reasons only over the survivors and proposes hypotheses, each citing evidence IDs.

emits → EV-… evidence, H-… hypotheses
engine → evidence.ts, hypothesis.ts
STAGE 3

Verify & score

Every hypothesis passes a deterministic citation gate, then the survivors face an adversarial entailment check. Rejected claims are recorded, and a grounded confidence percentage is computed in code for the ones that live.

emits → verdicts, confidence %, rejections
engine → verifier.ts
STAGE 4

Report

The report writer sees only verified findings — it never sees a rejected hypothesis. It writes the summary, a narrative with inline citations, and recommended actions, and states each attack's confidence and whether a detector corroborated it.

emits → incident summary, timeline
engine → report.ts
Why Stage 1 is not an LLM. The literal request was for agent 1 to convert the upload into a standard form. Doing that with a model would mean sending thousands of rows through a token budget, making the same file parse differently on different runs, and handing the prompt-injection surface a much larger door. The conversion still happens — it is just code, and the result is reported back to the UI as an inspectable standardisation report.
05

The four agents

Each agent makes exactly one structured LLM call per incident. Their input, output, and limits are fixed by schema, so a malformed or over-eager response fails validation instead of leaking into the record.

AGENT 1/4

Evidence Collector

Job
Retrieve this incident's events and signals, distil them into a small set of distinct, checkable facts, then ground them in code.
Reads
getIncident, getIncidentEntities, getIncidentEvents(60), getSignalsForEvents
Writes
evidence rows as EV-<incident>-<n>; an agent_runs audit row
LLM calls
1
Prompt rules
Cite real event IDs only; never invent one; no speculation about intent or attribution; few strong facts beat many weak ones.
Grounding gate. After the model answers, code checks every cited event ID against the events actually retrieved. A fact whose citations all fail is dropped, and the drop is recorded on the run.
AGENT 2/4

Hypothesis / ATT&CK

Job
Reason over grounded evidence only, look up candidate ATT&CK techniques, and propose hypotheses that each cite supporting evidence.
Reads
searchAttackKb — seeded with the incident's existing techniques plus keywords pulled from the evidence facts
Writes
agent_runs output {hypotheses, kb_techniques}
LLM calls
1 (maximum 6 hypotheses)
Prompt rules
Use only the listed evidence; every hypothesis cites at least one evidence ID; pick the single best-fitting technique; actions are simulation-only.
Citations that do not match stored evidence are stripped here. An empty citation list is left alone on purpose — the verifier's gate is what rejects it, in one place.
AGENT 3/4

Verifier

Job
Try to break every hypothesis. Reject anything the cited evidence does not establish on its own, then score what survives.
Reads
getSignalsForEvents on the cited events, to compute the detector component
Writes
Rejections into agent_runs.unsupported_claims; the confidence assessment
LLM calls
1 — and only if at least one hypothesis survived the citation gate
Prompt rules
Adversarial fact-checker. Support only if the cited text alone proves the statement. Never charitable. Rate evidence strength from the shown text, never from prior knowledge.
Fail-closed. No verdict returned, an empty citation list, or a citation that does not resolve — all three end in rejection. Silence is never treated as agreement.
AGENT 4/4

Report Writer

Job
Turn verified findings into the analyst-facing report. It is never shown a rejected hypothesis.
Reads
Supported hypotheses, their evidence, the event index, the confidence assessment — no database reads of its own
Writes
incidents.summary and mitre_techniques, plus one incident_timeline row per used evidence fact
LLM calls
1
Prompt rules
Assert nothing unsupported; inline [EV-x] citations next to factual narrative claims; state each attack's confidence and say plainly when it rests on the dataset's label; say so when evidence is thin.
Because the graph returns without calling this agent when zero hypotheses were supported, a fully-rejected incident writes no report and its status stays open.
06

The trust chain

The contribution of this project is that a sentence in the final report can be walked backwards to a number produced by a deterministic detector on a stored row. Nothing in the chain is asserted by the model.

claim H-INC-…-1 A hypothesis the model proposed, e.g. "a volumetric flood from 172.16.0.1 targeted 192.168.10.50:80".
Gate A · code Every citation must exist in the evidence table. Empty list, or one unresolvable ID, is an immediate rejection.
fact EV-INC-…-1 One evidence fact, itself already filtered so that its source_event_ids point at events that exist.
Gate B · LLM Shown only the cited evidence text, an adversarial pass asks whether that text, alone, establishes the claim. Anything broader than its evidence is rejected.
row event_id The stored flow record, with its timestamp, endpoints, ports and raw feature JSON.
signal R-NET-FLOOD · 0.97 The detector that fired on that flow, and the score it assigned — read from the database, not from the model.

How the confidence percentage is produced

The model does not get to say how confident it is. It supplies one number — how completely the cited text entails the claim — and code multiplies it by the strongest real detector score behind those same events. 

// agents/src/agents/verifier.ts — computed in code, for supported claims only
confidence_pct = detector_component × entailment_component × 100

detector_component   = max score over the behavioural signals on the cited events
                       (ANNOTATION_SCORE = 0.5 if the only backing is a dataset label,
                        0 if there is nothing behind it at all)
entailment_component = the verifier's evidence_strength for that claim (default 0.5)

Two consequences worth understanding. First, an LLM cannot inflate a score — the detector half is read from signals, so a claim about a flow no detector flagged is capped at 50%. Second, every assessment carries a basis label so the UI can never present an annotation-only finding as if an independent detector had confirmed it:

behavioural behavioural+annotation annotation-only
07

What it detects — and what it only carries

This is the section to read before demoing the project, because it is where the honest boundary sits. There are three tiers of capability, and only the first is detection in the strict sense.

Tier 1 — independently detected

3 attack families

Real behavioural detectors over flow features. No label involved. These produce genuine true/false positives and are what the detection metrics measure.

T1110 brute force T1498 flood T1071 beaconing

Tier 2 — carried and investigated

18 labelled attack classes

When the uploaded file has a label column, 43 signature patterns map non-benign labels to a canonical class and technique. These flow through the agents and get reports — flagged as an annotation, never as detection.

SQL Injection XSS Port Scanning Ransomware Phishing +13 more

Tier 3 — not supported

Unlabelled, non-flow attacks

A file with no label column, or logs that are not network flows at all, produces nothing. The parser rejects it with a clean error explaining which canonical columns were missing — it does not crash and it does not invent incidents.

The behavioural detectors

Detector refFamilyFires whenScore
R-NET-BRUTEFORCEbrute_force Destination port is 21 or 22 and ≥30 flows hit the same (src, dst, port) min(0.95, 0.6 + log₁₀n⁄8)
R-NET-FLOODflood Destination port is not 53 or 123 and ≥3000 flows hit the same (src, dst, port) min(0.97, 0.7 + log₁₀n⁄10)
flow_rate_zscoreflood Flow packet rate is more than 3 standard deviations above the file's mean — a statistical corroborator that folds into the flood family min(0.9, 0.4 + z⁄40)
R-NET-BEACONbeacon Internal host → external host on a non-web port, ≥20 flows, and at least 3 distinct internal sources reach that same destination 0.75 + min(0.2, fan-in⁄50)

How one flow becomes exactly one incident

A flow can trip two families at once — a high-volume SSH attack satisfies both the brute-force and the flood thresholds. If both claimed it, the same event would appear in two incidents and quietly re-introduce cross-scenario leakage. So ownership is assigned once, by fixed priority: 

# the sort key is (family priority, then -score, then key)
brute_force(0)  >  beacon(1)  >  flood(2)  >  labelled(9)

# priority must come FIRST, not score: the flood detector caps at 0.97 and the
# brute-force detector at 0.95, so an argmax on score alone would file a port-22
# credential flood under DDoS. Annotation families rank last by design.

cluster keys:  brute_force → (src, dst)     flood → (dst, dport)
               beacon → (dst,)              labelled → (dst,)

The eval-integrity guard

When a file has labels, it is tempting to count the label signal as a detection and report a perfect F1. That would be scoring the label against itself. Instead the behavioural verdict is captured before the annotation is appended, so the confusion matrix always measures the real detectors: 

sigs = detect(row, idx, aggs, SCEN)
pred = len(sigs) > 0        # ← behavioural verdict, captured HERE
…
if has_label and is_attack:
    sigs = sigs + [label signal]   # appended after — never counted as a prediction

Alongside the metrics, each class gets a corroboration rate: of the flows the dataset annotated as this attack, what share did an independent detector also flag. This is the number that tells you whether the annotation is backed by anything.

Two contrasting results, both real. On a DDoS slice, corroboration is 100% and F1 is 1.0 — the detectors genuinely see it. On a SQL-injection slice, corroboration is 0% and F1 is 0.0. That 0.0 is the guard working: a self-scoring implementation would have reported 1.0 and been lying.

Data model

Eleven tables plus one for upload batches, defined across three migrations in supabase/migrations/. Everything an analyst reads is in Postgres; the browser never writes to it.

TableHoldsKey columns
eventsOne normalised log recordevent_id, ts, src_ip, dst_ip, severity, mitre_tags, raw
signalsOne detector hit on one eventsignal_id, event_id, detector, detector_ref, score, reason
detection_rulesThe rule catalogue shown in the UIrule_id, title, detector, mitre_tags, severity
alertsDeduplicated detector signals, per entityalert_id, confidence, contributions, event_ids[], incident_id
incidentsThe correlated caseincident_id, code (unique), risk_score, risk_factors, summary, status
incident_entitiesActors, targets and victims of a case(incident_id, entity_type, entity_value), role

incident_timelineChronology built from used evidenceincident_id, ts, label, evidence_id

Who can write what

Row-level security is enabled on every table with exactly one policy each: for select to anon, authenticated using (true). There is no insert, update or delete policy anywhere. The consequence is a clean split:

  • The browser holds the anon key and can read everything, write nothing.
  • The local Node backend connects with the secret DATABASE_URL and performs every write — batch inserts, evidence, agent runs, reports.
The backend is unauthenticated by design. It binds 127.0.0.1, runs uploaded CSVs through the parser, and writes with a credential that bypasses RLS. It must never be exposed beyond localhost, and CORS stays restricted to the dev origin.

Batch isolation is a second axis of separation. Every UI upload creates an ingest_batches row that is stamped onto its events, signals, alerts, incidents and entities. The seeded CICIDS baseline keeps batch_id = NULL and appears in the UI as the "CICIDS Seed" dataset.

09

Tech stack

The stack is frozen. Stability is worth more than architectural purity at this stage, and every substitution below was chosen because the alternative was not worth the migration risk.

LayerWhat we useWhy this, and not the obvious alternative
Frontend React 19 · TanStack Start + Router · Tailwind v4 · Radix/shadcn · Recharts · Vite File-based routing with a shared analyst shell. No Next.js — the routing need is small and this keeps SSR out of the way of a read-only dashboard.
Backend Node 24 · Express · multer · pg · tsx Needed for exactly two things RLS forbids the browser from doing: writing to Postgres and spawning the Python analyser.
Detection Python 3 · standard library only No pandas, no scikit-learn, no psycopg. The files are 70–170 MB and must stream; the stdlib csv reader does that without a dependency or an install step.
Agents LangGraph.js · zod structured output LangGraph in TypeScript rather than Python so the graph shares the backend's DB pool and types. Every agent output is schema-validated.
LLM Google Gemini via @langchain/google-genai Free tier. Calls are serialised process-wide at ≥13 s apart to stay under the rate limit — which is also why only one upload can run at a time.
Database Supabase Postgres · RLS · PostgREST Gives the browser a read API for free. ClickHouse and Kafka were both cut as irrelevant at this scale.
Deep learning Hand-written numpy MLP 69 → 64 → 32 → 1, ReLU, sigmoid, Adam. Written from scratch because PyTorch is not installed on the target box and the architecture is frozen — see section 12.

Two processes, one database. The frontend will load without the backend, but uploads and investigations will not run.

Copy .env.example to .env at the repo root and fill it in. Both .env and web/.env.local are gitignored; the example file keeps placeholders only. Never commit a real value.

From zero to a running demo

# 1 — dependencies
cd agents && npm install
cd ../web && npm install && cd ..

# 2 — database schema (all three migrations, in order)
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/migrations/0001_init.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/migrations/0002_alerts_rls.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/migrations/0003_batches.sql

# 3 — the seeded CICIDS baseline (needs the raw CSVs, see the note below)
python3 ml/ingest_cicids.py
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f data/cicids_seed.sql

# 4 — two terminals
cd agents && npm run server     # backend on 127.0.0.1:8787
cd web    && npm run dev        # frontend on http://localhost:5173
Do not use scripts/load_db.sh to set up a fresh database. It applies only 0001 and the synthetic seed — it never applies 0002 or 0003. A database loaded that way has no RLS policies and no ingest_batches table, so batch filtering and the whole upload path fail. Run the three migrations explicitly, as above.

The rejected claim, in full

On INC-2017-0002 the hypothesis agent asserted that "multiple hosts including 192.168.10.8 made repeated or multiple connection attempts via SSH to target 192.168.10.50 on port 22, indicating possible credential guessing behaviour."

The verifier checked the citations and found that EV-INC-2017-0002-1, -2 and -4 each record a single connection attempt, from 192.168.10.16, .17 and .19 — not repeated attempts from 192.168.10.8. The claim was broader than its evidence, so it was rejected and no report was written for that run.

This is the demo's headline. A plausible, well-written, entirely wrong attribution was caught by the citation gate rather than reaching an analyst.

The same incident, after the retrieval fix

That rejection had a second cause worth understanding, because it is the project's best bug story. INC-2017-0001 and INC-2017-0002 share an actor and a target IP, so the original evidence retrieval — "fetch every event where this IP is source or destination" — pulled the SSH flows and the HTTP flood flows into the same evidence packet. The model saw port-22 traffic inside a DDoS incident and reasoned about it correctly given what it was shown.

The fix is one query: evidence is now scoped by the incident's own alerts.event_ids, with the entity-IP lookup kept only as a fallback. Re-running INC-2017-0002 afterwards produced a single grounded fact, one supported hypothesis, and a correct T1498 volumetric flood report. The wrong hypothesis was not suppressed — it was never formed, because the evidence no longer supported it.

Known limitations and gotchas

Read this before presenting. Every item here is something a sharp examiner could otherwise raise, and having the answer ready is worth more than hoping it does not come up.

LimitationWhy it exists, and what to say
Three independently detected attack families The detectors are real but few. Two attacks that work correctly beat ten that do not; the label bridge extends coverage honestly rather than by pretending.
Botnet detection is weak (F1 0.53) Low-and-slow beaconing is genuinely hard on per-flow features. State it as a measured limitation, not a hidden one.
The MLP is offline only The architecture was frozen to protect the graded agent loop. It is an evaluation artifact.
No live collection Ingestion is file-based and offline. A live collector was explicitly out of scope.
The backend is unauthenticated It is designed for 127.0.0.1 only and must never be exposed. This is a stated deployment boundary, not an oversight.
Free-tier quota governs the demo Calls are throttled to one per 13 seconds and uploads are serialised. Only one analysis runs at a time; a second upload is refused with HTTP 409 and a clear message.
A rejected incident is invisible over the read API With no report, its status stays open — indistinguishable from "still running". The backend's in-memory job store carries the real terminal state, which is why the UI polls it.
Uploads are truncated at 12 incidents Each incident costs LLM quota, so a many-class dataset is cut to the twelve highest-risk and the drop is reported in the UI. It is never silent.

Smaller things that will bite

  • alerts.incident_id is a bare column with no foreign key, despite the migration comment implying one. Do not rely on referential integrity there.
  • web/src/lib/soc-snapshot.ts is a static fallback snapshot with no importers. It is leftover from the unconnected-preview mode.
  • Empty trailing rows in CICIDS files are treated as benign. This is harmless but it is why a file can report more rows read than rows standardised.

done_no_report is a success, not a failure. It means every hypothesis was rejected — the verifier did its job and the system declined to write a report it could not support.

Vocabulary worth being precise about

  • Detector — behavioural code that flags a flow. Only four of these exist.
  • Signal — one detector's hit on one event, with a score and a reason.
  • Annotation — a non-benign label from the uploaded file, carried through and clearly marked. Never described as detection.
  • Corroboration — an independent detector flagged the same flow the label called an attack. The percentage is the honesty metric.
  • Grounding — a claim's citations resolve to stored evidence. Failing this means the claim is dropped.
  • Entailment — the cited evidence, on its own, establishes the claim. Failing this means the claim is rejected.
